# Reinhardt Cloud Dashboard

The Dashboard and Control Plane use Reinhardt Web **0.4.0-alpha.20** with
Pages SSR and WASM hydration. Application styles are generated by `style!`;
no external CSS framework is loaded.

The application contains eight Apps generated with `startapp`: `identity`,
`organization`, `project`, `source`, `deployment`, `cluster`, `secret`, and
`observability`. Each owns its persistence and policy services; the root router
only composes their routes. PostgreSQL ORM models register with the framework's
migration system. Model aggregators re-export one definition per file. Cross-App
test implementations live under scoped `tests/integration/` and `tests/e2e/`
directories with stable root Cargo targets. Eight initial and four incremental
migrations are included.

The current application provides the project-list presentation, English and
Japanese catalogs, responsive light and dark styles, and domain rules for
permissions, operation recovery, source execution, cluster admission, secret
references, and bounded logs. Password sign-in creates a revocable PostgreSQL
session; each request reloads the account and organization membership. The browser
selects an organization before displaying its projects. Platform administration
does not bypass organization access checks. Project detail shows each Environment's
desired runtime inputs and latest persisted operation. Language selection survives
navigation and reload. Desired replicas and operation acceptance do not establish
application readiness.

Runtime operation services accept restart, fixed-replica scaling, and CPU
autoscaling after reloading current account, membership, production grant,
Environment ownership, registered cluster capabilities, and allocation limits.
An Environment row lock serializes conflicting acceptance. One transaction writes
the versioned desired configuration, operation, bounded dispatch envelope, and audit.
A matching idempotency key replays the original operation; changed contents are
rejected. Unfinished and uncertain operations block conflicting changes. Receipts
and results must match the assigned cluster, Operation ID, and Environment version.
Pending envelopes remain in PostgreSQL across connection or process replacement;
delivery receipt is distinct from execution success. A ten-minute runtime deadline
records uncertainty even when a receipt is missing.

Pages routes have dedicated App components: `/login/`, `/organizations/`,
`/organizations/{organization_id}/projects/`, and
`/organizations/{organization_id}/projects/{project_id}/`. The Project routes share
an organization layout with an `Outlet`; links reverse registered route names.
Direct navigation renders authenticated SSR and hydrates the existing DOM. The
first internal link activates `ClientLauncher`, which owns subsequent client
transitions and browser history without replacing the document.

Organization and Project reads use typed `server_fn` query descriptors. Environment
controls submit typed runtime mutations with pending guards, idempotency keys and
expected versions, then invalidate the Project detail query. An unfinished operation
disables further controls. Native sign-in/out forms work before WASM loads.
The generated `X-CSRFToken` header is verified against the signed HttpOnly cookie
and exact Origin; the initial document supplies the token through framework metadata.
Authentication and organization authorization are resolved from the session on every
function call, including after query invalidation.

Agent delivery transports and deployment execution remain planned integrations.

## Development

Use Rust 1.96.0 and the `wasm32-unknown-unknown` target. Docker is required for
infrastructure tests. Copy the non-secret settings templates before starting:

```bash
cp settings/base.example.toml settings/base.toml
cp settings/local.example.toml settings/local.toml
```

Provide `CLOUD_SECRET_KEY` and `CLOUD_DB_PASSWORD` through the process
environment. `CLOUD_DB_HOST`, `CLOUD_DB_PORT`, `CLOUD_DB_NAME`, and
`CLOUD_DB_USER` override the PostgreSQL defaults. Production cookies are
secure; local HTTP settings relax that requirement only in the local profile.
Set `CLOUD_PUBLIC_ORIGIN` to the browser's exact origin, including its scheme and
port and excluding a trailing slash. The local default is `http://localhost:8000`.
Production requires an HTTPS origin. Signed CSRF tokens and Origin checks protect
browser mutations. Session and CSRF cookies use `HttpOnly` and `SameSite=Strict`;
production adds `Secure` and the `__Host-` prefix. Session tokens are stored only
as SHA-256 hashes and expire after 24 hours.
`CLOUD_SETTINGS_DIR` selects a mounted settings directory. Relative paths resolve
from the Dashboard project root; the default is its `settings/` directory.

From this directory:

```bash
cargo run --bin manage -- makemigrations --state-source files
cargo run --bin manage -- migrate
cargo run --bin manage -- createplatformadmin admin@example.com
cargo make publish-pages
cargo run --bin manage -- runserver --with-pages --asset-manifest dist/manifest.json --no-spa --noreload --no-wasm
```

The bootstrap command reads `CLOUD_BOOTSTRAP_PASSWORD` from its environment;
provide a password of 12 to 1024 bytes. It creates the administrator, personal
organization, and Owner membership in one transaction. It requires only the
selected database settings and rejects duplicate email addresses. Unset the
bootstrap password after use. Public self-registration is unavailable.

`GET /healthz/` reports process liveness only; it does not establish database
or cluster readiness.

`GET /` renders the access state on the server before the WASM client starts.
Hydration preserves the server-rendered DOM and activates catalog-backed language
controls. Documents without SSR state mount registered client routes instead.
The explicit asset manifest selects the published generation when settings are
mounted outside the project directory. The document uses one verified asset generation, including generated component
styles and the Pages loader. Republish assets and restart the server after
frontend changes. `publish-pages-release` uses an optimized WASM build before
publication; published files must not be modified after their hashes are recorded.

Alpha.20 does not include the PostgreSQL binary mapping fix in
[reinhardt-web#6637](https://github.com/kent8192/reinhardt-web/issues/6637).
The secret model therefore uses text for encoded ciphertext, tracked in
[Cloud#912](https://github.com/kent8192/reinhardt-cloud/issues/912). Secret encryption
and delivery are not yet connected to this persistence model.

From the workspace root:

```bash
cargo test -p cloud_dashboard
cargo check -p cloud_dashboard --lib --target wasm32-unknown-unknown
cargo fmt --all --check
```

Native integration tests start disposable PostgreSQL, load copied settings,
apply all twelve migrations twice, and check the persisted ledger. HTTP tests
exercise administrator bootstrap, CSRF and Origin rejection, organization
isolation, live permission changes, expired and inactive sessions, and logout
revocation. Explicit session-expiry fixtures use microsecond precision so they
can be encoded as PostgreSQL timestamp parameters. Containers, servers,
connections, and settings directories are owned
by guards and dropped after testing. Operation tests cover concurrent replay,
version conflicts, production grants, capability and replica admission, correlated
receipt and result handling, uncertainty, and rollback when audit persistence fails.
Read APIs include `GET /api/v1/organizations/`, `GET /api/v1/projects/?organization=...`,
and `GET /api/v1/project/?organization=...&project=...`.

The browser test is opt-in because it requires a published WASM generation and
Playwright's Chromium. Set `CLOUD_BROWSER_NODE` to the Node executable and
`CLOUD_BROWSER_PACKAGES` to the directory containing `playwright`; optionally set
`CLOUD_BROWSER_EXECUTABLE` to an installed Chromium executable. After publishing:

```bash
cargo test -p cloud_dashboard --test browser -- --ignored
```

It starts its own PostgreSQL and Control Plane, seeds a real uncertain operation
through the shared acceptance service, and checks SSR DOM preservation, hydration,
authentication, organization isolation, typed query requests, client navigation and
browser history, runtime mutation acceptance/replay/conflict, query invalidation,
locale persistence,
keyboard controls, mobile width, dark styles, and browser exceptions.
Set `CLOUD_BROWSER_EXPORT_SCREENSHOT` to an absolute output path to export the
verified project-detail view for documentation. The temporary browser artifacts
are deleted with their owning test directory.
